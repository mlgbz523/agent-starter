# 线上故障应急响应与可观测性手册 (INCIDENT_RESPONSE.md)

> **使用说明**：线上系统发生故障时，PM 与 Agent 协同快速定位、止血与复盘的标准排错 SOP。

---

## 一、 故障应急止血三原则
1. **先止血，后排错**：如果线上服务中断或核心数据错乱，第一优先级是切断流量或由**运维/技术人员执行回滚**（Agent 严禁进入生产环境，仅负责输出《回滚止血操作卡片》供人类执行；**注意：仅在本次发布包含数据库变更时才需先跑 `down.sql`**，无数据库变更切勿盲目执行，避免误伤数据）。
2. **保护现场数据**：收集最新的 100 行异常堆栈日志与系统指标，保存现场快照。
3. **隔离复现**：将报错信息与脱敏数据复制到**测试环境 (TEST)**，再让 Agent 介入排查。

---

## 二、 快速排查标准指令链 (由 Agent 快速定位)

当向 Agent 汇报线上故障时，执行标准化诊断流程：

### 步骤 1：日志与关键堆栈检索
要求 Agent 仅提取关键错误行，杜绝翻阅几万行无用日志：
```bash
# 提取最近 50 条包含 ERROR / Exception 的堆栈
tail -n 500 server.log | grep -E "ERROR|CRITICAL|Traceback" -C 3
```

### 步骤 2：生成故障三句话白话诊断报告
Agent 定位后，必须以以下结构向 PM 汇报：
- **故障现象**：发生了什么错误（如：用户支付回调超时返回 504）。
- **根本原因**：为什么会发生（如：数据库连接池耗尽，存在未释放的连接）。
- **修复方案与风险**：准备改动哪里，是否有改动其他业务的风险。

---

## 三、 质量与成本每周度量看板 (Weekly Metrics)

为确保“省 90% 额度”和“交付质量”有据可循，建议每周五由 PM 或 Agent 执行一次度量统计：

| 评估指标 | 目标基准线 | 本周实际数据 | 状态评估 (正常/预警) |
| :--- | :--- | :--- | :--- |
| **Token 额度消耗** | 控制在预算内 (无异常激增) | — | 正常 |
| **同类错误熔断次数** | 每周 < 2 次 (若超限说明架构有硬伤) | — | 正常 |
| **PM 验收打回次数** | 每周 < 1 次 (验收三信号未通过) | — | 正常 |
| **线上回归 Bug 数量**| 0 级高危故障，低危 < 2 个 | — | 正常 |
| **单任务会话长度** | 平均会话轮次 < 8 轮 (杜绝历史滚雪球) | — | 正常 |
