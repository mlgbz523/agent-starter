# AI 研发协作 PM 使用手册 (零技术基础指南)

> **写在前面**：本手册是专门写给你（项目经理 / PM）看的实战指南，而不是写给 AI Agent 看的提示词。
> **核心原则**：你不需要懂代码，你的职责是**把控业务目标、验收用户体验、守住安全底线**。Agent 必须替你把所有技术细节翻译成业务常识。

---

## 一、 角色认知与核心底气

1. **你不是代码质检员，你是业务裁判**：
   - 不用去读代码里的 `function`、`class` 或语法。
   - 你只需关心三件事：**用户能用吗？数据安全吗？做错了能撤销吗？**
2. **AI 是你随叫随到的工程师 + 导师**：
   - 任何时候看不懂 Agent 说的词，直接回复：“用大白话解释，打个生活类比”。
   - 遇到任何疑问，你可以用自己的话复述一遍并问它：“我理解得对吗？指出我的错误”。

---

## 二、 如何向 Agent 提需求 (防跑偏与防膨胀)

### 1. 提需求黄金三段式
向 Agent 交代任务时，尽量按照以下格式：
- **场景与目标**：“用户在 [什么页面/什么情况下]，希望能够 [进行什么操作]。”
- **预期看到的效果**：“点击后应该看到 [弹窗提示/颜色改变/数据增加]。”
- **限制边界（可选）**：“先别碰其他页面，只改当前这个小功能。”

### 2. 面对 Agent 反问时怎么回答
- Agent 会主动向你复述需求，并最多问你 1~3 个业务问题；
- 每个问题它都会附带一个“推荐默认值”；
- **极简应对法**：如果你觉得推荐值符合业务常识，**直接回复：“按你的推荐来”**，不用自己费心编排技术细节。

### 3. 如何防止 Agent 擅自“添枝加叶”
- Agent 有时会顺手提出“我建议顺便把某个接口也重构了”；
- 只要这不是你这次要解决的核心问题，**坚决回复：“本次不做，先跑通主需求”**。

---

## 三、 手把手教你看“PM 决策卡片”

当 Agent 遇到技术分支或方案权衡时，必须向你呈报标准【PM 决策卡片】。你只需按以下顺序扫一眼：

| 检查项 | 你需要关注的核心问题 | 怎么选 |
| :--- | :--- | :--- |
| **1. 耗时与额外成本** | 哪个方案今天就能跑通？哪个要多花钱或耗很多天？ | 优先选耗时短、零额外成本的 |
| **2. 对用户的影响** | 哪个方案会让用户体验更好、不改变老习惯？ | 选对已有功能冲击最小的 |
| **3. 最坏情况** | 如果这个方案做砸了，后果严重吗？ | **重点看最坏后果！** 如果写着“可能丢失数据”，坚决不选 |
| **4. 能否撤销** | 选错了能一键退回吗？ | **优先选容易撤销的方案！** |

> 💡 **黄金兜底口诀**：**“拿不准就选推荐方案（通常改动最小、最容易撤销）；不想选就不回复，Agent 绝不敢擅自做主。”**

---

## 四、 遇到哪几种情况应当“拒绝批准”

当 Agent 弹出【高危操作审批申请】时，凡命中以下任意一条，**直接打回并拒绝**：

- ❌ **后果不可逆**：卡片上写着“无法撤销”或“需要手动重新建库/重建数据”；
- ❌ **影响范围不明**：影响面写着“未知”或“可能影响全系统所有模块”；
- ❌ **含糊其辞**：没有给出明确的推荐意见，或者解释像纯技术黑话；
- ❌ **关键措施缺失**：要修改数据库结构，但没有附带回滚脚本（`down.sql`）；
- ❌ **想动规则文件**：Agent 提出想修改 `AGENTS.md` 或 `.agents/rules/`（坚决拒绝，除非是你自己发起的规则调整）。

## 五、 不懂代码，如何完成 100% 可靠的验收

### 1. 查验“完成声明三分法”
Agent 交付时，必须呈报三分法看板。你只需盯紧两块：
- **重点看 ⚠️【未验证】**：看它没测的地方是不是核心场景（例如：“未测试弱网环境”、“未测试批量输入”）。如果是关键场景，命令它：“把这部分也测完再交”。
- **重点看 ❓【不确定】**：看它坦白的不确定点，要求它说明最坏会有什么影响。

### 2. 亲手跑一遍演示步骤 (零基础)
- Agent 必须提供“**打开哪里 -> 点什么 -> 应该看到什么**”三段式说明；
- 如果必须执行命令，它必须给出你**直接复制并回车**的一行命令；
- 你亲手点一遍，如果看到的现象与它描述的不符，**无需分析原因，直接截图甩给它**：“现象不一致，看截图修复”。

### 3. 看一眼改动文件清单 (Diff 三件事)
- 改了几个文件？（如果只是改个按钮文案，改了 5 个文件绝对有问题）；
- 增删了多少行？（改动几十行正常，大几百行要警惕）；
- 有没有改到无关文件？（比如改前端页面，动了后端数据库配置）。

## 六、 看到哪些危险信号应当立刻“叫停”

在开发过程中，一旦看到以下信号，请立即输入**“暂停，先停下来”**：

1. 🚨 **死循环报错（触发熔断）**：同一个报错 Agent 连续修改了 2 遍还在报错；
2. 🚨 **作弊偷懒**：发现 Agent 试图修改测试断言、删除既有测试、加 `@skip` 或关闭代码检查来让结果变绿；
3. 🚨 **改动像滚雪球**：原本只想修一个小 Bug，Agent 报告里列出的待修改文件越来越多；
4. 🚨 **失忆胡说**：换了新对话窗口后，Agent 遗忘了之前的决定，打算推翻重来。

---

## 七、 你的终极“后悔药”机制

- 每个任务启动前，Agent 已自动创建了还原点。
- 只要任何时候你觉得“改乱了”、“局面不受控”或者“做出来的不是我想要的”：
- 👉 **直接对 Agent 发一句：“撤销刚才的修改，退回到任务开始前。”**
- Agent 将无条件回滚所有改动，并向你汇报已安全复原。

---

## 八、 关键红线节点的“外部独立保险”提醒

> ⚠️ **强烈提醒**：虽然本体系已经替你建立了层层卡片与安全防线，但在**涉及真金白银与生产核心资产的节点**：
> 1. 首次正式线上发布；
> 2. 正式库的大规模表结构变更；
> 3. 清空或迁移历史数据；
> 4. 开通会产生实际计费的第三方 API。
>
> 在你点击“批准”前，**强烈建议找一位懂技术的同事或顾问朋友，把 Agent 给你的审批卡片发给他看一眼（30 秒即可确认）**。这是为零技术背景团队上的最后一道物理独立保险！

## 九、 PM 边做边学：三阶段个人成长路线图

把 Agent 当作随叫随到的导师，建议按照以下节奏循序渐进掌握核心常识（不用学写代码）：

| 阶段 | 核心概念 (遇到就让 Agent 结合业务做类比) | 你的掌握标志 |
| :--- | :--- | :--- |
| **第一阶段：先学基础** | Git 提交/分支/回滚、前端与后端区别、数据库表、环境变量与密钥 | 能看懂改动文件清单，会用“撤销刚才的修改” |
| **第二阶段：再学架构** | API 接口原理、自动化测试为什么能当验收依据、外部依赖是什么、开发/测试/生产三套环境 | 能读懂“完成声明三分法”，会用演示步骤验收 |
| **第三阶段：后学运维** | 上线部署流程、数据库迁移 (`down.sql`)、监控与日志排错、权限与安全防线 | 能独立审阅“高危审批卡片”，知道何时拉人复核 |

## 十、 对话变长、Agent 犯迷糊？如何开启新会话 (Memory Bank 零遗忘交接)

AI 并不是神仙，当对话超过 15~20 轮、或者屏幕里刷满了成百上千行终端报错日志时，它的注意力会被杂质稀释（就像一个人连续加了 24 小时班开始走神）。

此时硬撑着继续对话不仅反应变慢，还会引发**“幻觉”**（明明没改过的代码它说改了，或者忘了最初的约定）。

### 🛠️ 3 步物理清空杂质、零遗忘续接法：
1. **叫它落盘**：对它说一句：**“请更新 PROGRESS.md，准备交接卡片。”**（Agent 会把所有现状、未完成细节 100% 写入本地看板）；
2. **点新建对话**：点击 IDE 界面左侧或顶部的「+ / 新建对话 (New Chat)」；
3. **唤醒新会话**：在全新的对话框里，直接粘贴这句话并回车：
   > **“继续按照 docs/PROGRESS.md 推进。”**
4. **效果**：新会话的 Agent 拥有 100% 满血的注意力和纯净上下文，同时依靠本地账本完整继承前序所有工作，真正做到**零遗忘、零幻觉、秒级续接**！
