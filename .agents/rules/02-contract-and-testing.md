# 02 — 契约与测试

## 适用范围
仅对软件设计、编码、重构、配置和可执行系统验证生效。纯界面风格调整优先走 `09-ui-design-standard.md`；非软件文档任务不要求创建代码测试。

## 1. 契约先行
- 对影响公共接口、持久化结构、模块边界或关键数据流的变更，先明确输入、输出、约束和错误行为，再开始实现。
- 使用项目适合的表达方式（例如 TypeScript 类型、JSON Schema、Pydantic 模型或接口文档）；不要为了形式主义给每个微小改动都创建独立契约文档。

## 2. 大改动前计划
- 触发条件：新增模块/持久化数据/核心流程，存在多个实质不同的架构选项，关键边界尚未定义，或预计受影响文件总数达到或超过 3 个。核心公共契约、持久化结构和核心流程变更属于独立触发条件，不受文件数量限制。对常规同模块协同改动和纯界面任务按具体规则判断，不机械按文件数审批。
- 写代码前在项目约定位置形成简明计划，列明新增、修改、不动的范围和 3–5 条可核验验收标准；若项目使用 `docs/task_plan.md` 或 `docs/design/`，沿用其约定，不盲目创建重复文档。
- 需用户批准的任务，必须等到明确批准后才修改受门禁约束的源码。计划批准不等于获准提交、发布或推送。
- 设计图作为同一计划的一部分，不另建重复审批链。纯界面任务依 `09`。

## 3. 验收门禁
- 根据需求选择测试、构建、静态检查、手工检查、浏览器/真实环境验证等适当方式。
- 软件交付应运行相关测试；项目具备全量测试套件时，评估并运行全量套件，不只运行新增用例。
- 报告实际命令、实际输出/摘要与退出码（若有）；没运行就标注未运行，环境受阻就说明受阻原因。
- 测试全绿是必要证据之一，不自动证明业务需求全部满足；关键需求应映射到对应的行为或验证证据。

## 4. 测试质量与防作弊
- 不得为了让测试变绿而删除/削弱既有断言、无理由添加跳过项或关闭检查规则。
- 需求变更确实要求调整测试时，说明旧断言为何不再适用、新验收行为是什么，并按当前项目的审批规则处理。
- 对关键测试可采用反向验证/故障注入，确认它能识别目标缺陷；只在安全、隔离且可恢复的环境中执行，不要在真实生产数据上故意破坏逻辑。
- 无测试底座的新软件项目，可建立与项目规模相称的最小测试方式，并记录实际验证过的命令；不要仅因文档要求而搭建过度复杂的测试体系。

## 5. 动态范围升级铁律（Scope Escalation）

任务初始判定为小任务后，执行过程中发现以下任一情况时触发：
- 预计受影响的文件总数达到或超过 3 个；
- 涉及核心公共接口、共享数据契约、持久化结构或核心业务流程的变更（此条件独立于文件数量）；
- 原定方案需要显著扩大模块修改范围，可能改变已确认的实施方案、风险或验收标准。

**强制动作**：
1. 立即挂起新增代码写入，已完成的修改予以保留，不得擅自回滚或清理；
2. 重新评估任务范围，列出已修改、预计需要修改及明确不修改的文件或模块，并说明触发升级的原因；
3. 按大任务流程补齐设计说明、契约、测试方案和新增验收标准；
4. 向用户提交范围升级说明，明确新增工作、影响、成本、风险和回退方式；获得用户明确确认后才能继续新增源码修改。

不得通过拆分提交、分批修改或漏计间接影响文件的方式规避触发条件。若同时涉及安全风险、数据丢失或其他高危操作，应同时执行对应的安全门禁。

## 6. 大任务首次写入门禁

- 需要设计方案审批的大任务，Agent 在首次修改源码前，必须明确声明设计方案及范围已获得用户确认，并能对应到用户对当前方案和范围的明确确认记录。Agent 自己判断"已获批准"不构成审批证据。
- 用户尚未确认方案时，只允许进行只读检查、影响范围分析、设计编写和测试方案准备；不得提前修改源码。
- 执行中触发动态范围升级或出现超出已批准方案的重大变更时，原有审批不能自动覆盖新增内容；须暂停新增修改，重新评估并取得必要确认后再继续。
- 不强制固定 TAG 格式（如 `[STATE: ...]`）。小任务按相应规则执行，无须增加重复的状态汇报。
