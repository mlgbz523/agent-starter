# 01 — 架构与模块化

## 适用范围
仅在软件架构、编码、代码审查或代码文件维护任务中使用。本规则不要求普通研究、学习或办公任务采用代码修改流程。

## 原则

### 1. 简洁、单一职责与明确边界
- 每个模块承担清晰职责；优先项目现有模块和语言标准能力，避免为假想需求过度抽象。
- 优先明确输入/输出、纯函数和显式依赖；避免意外的全局状态污染。
- 代码自研与依赖选择遵循 `04-reuse-and-supply-chain.md`，不要在本文件重复维护依赖准入清单。

### 2. 精准差异
- 修改已有代码时，优先做最小有效变更；不要全量重写无关区域或顺手格式化无关代码。
- 若重构、格式化本身就是用户目标，先明确其范围，不能把“外科手术式修改”误解为禁止必要的结构调整。
- 交付前检查差异，识别无关变更、未使用变量、临时调试输出和意外生成文件。

### 3. 定向检索与语义完整性
- 优先通过搜索定位符号、关键词、调用点和相关测试，再读取需要的上下文。
- 以完整函数、类、配置段或逻辑单元为读取单位；“300 行”是经验提示而非机械上限。必要时读取更大上下文，避免切碎导致误判。
- 不得因“先搜索”而省略理解调用链、异常路径或相邻契约所需的上下文。

### 4. 注释
- 注释重点解释原因、约束、边界或不明显的决策；避免重复代码表面行为的废话注释。

### 5. UI 与视觉风格分流
- 界面任务优先遵守项目根目录 `DESIGN.md`（存在且有效时），详见 `09-ui-design-standard.md`。
- 无有效设计系统时，先识别项目现有风格和用户目标；不要默认把“现代高质感”理解为必须增加动画、阴影或复杂组件。
- 仅在用户明确要求时启用互斥风格：极简/原生/性能优先，或高动效/宣传片/电影感。不要在没有需求依据时擅自引入动画库。
