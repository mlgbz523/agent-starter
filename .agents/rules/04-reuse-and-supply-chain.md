# 04 — 复用与供应链

## 适用范围
仅在软件实现、增加/升级依赖、安装 Agent 技能或使用外部开发工具时生效。非软件研究中引用某个工具，不自动等同于安装依赖。

## 1. 四层复用顺序

1. 项目已有模块和工具函数；
2. 语言原生标准库；
3. 项目已安装且适用的第三方依赖；
4. 必要时自研小型业务实现。

自研需说明必要性，尽可能保持职责单一、耦合低，并以测试覆盖公开行为和已知边界。100% 覆盖率是特定项目可以设定的目标，不是所有代码的通用质量证明；覆盖率数字不能代替断言质量。

## 2. 新依赖准入

- 安装或升级前核对包名、官方来源、版本、维护状态、许可证、已知漏洞和与现有依赖的功能重叠；真实性探针见 `03-hallucination-probes.md`。
- 依照当前工作区的许可证策略处理白名单、灰名单和禁止项。若本工作区沿用下列原策略，应明确把它当作**项目政策**而非“某许可证在所有场景下都安全/不安全”的普遍事实：
  - 直接允许：MIT、Apache-2.0、BSD-2/3-Clause、ISC、Unlicense；
  - 需审批：MPL-2.0、LGPL-2.1/3.0；
  - 禁止：GPL-2.0/3.0、AGPL、商业专有或无许可证声明。
- 许可证兼容性可能受分发方式、链接方式、产品策略和法律要求影响。无法判断时提交审批，不要凭名单本身下法律结论。
- Node.js 项目可在当前工具适用时执行 `npm audit --audit-level=high`；Python 项目可使用已安装且受支持的漏洞审计工具（例如 `pip-audit`）。记录真实输出和无法扫描的范围，不把扫描“未发现”写成不存在风险。
- 原策略包含“首次发布超过一年、近 12 个月活跃、未被标记 Deprecated”的维护门槛。实施例外时需单独说明理由并按项目授权规则审批；对短生命周期、官方新发布或低频维护项目应评估适用性，不要把单一提交频率机械当作安全结论。

## 3. PM 引入申请卡片

按当前工作区审批策略，申请卡片至少说明：包名和版本、白话用途、复用/自研代价、官方来源、许可证与漏洞状况、维护情况、替代方案、回滚方式及建议。未经要求的工具偏好不构成安装授权。

## 4. Agent 技能和外部工具

- 安装 Agent 技能前，先查看其说明文件和将执行的脚本；遵守当前工作区的技能安装方式，优先项目/工作区级隔离安装，避免不必要的全局安装。
- `gitingest`、`gitdiagram`、`Archify` 等参考工具按 `10-design-and-reference-tools.md` 处理；该规则不代表这些工具已经安装或已通过安全审查。
