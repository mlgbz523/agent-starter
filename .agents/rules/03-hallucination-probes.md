# 03 — 证伪验证与依赖探针

## 适用范围
本规则中的 CLI、依赖探针和测试条款面向软件/技术任务。跨任务的诚实与证据原则由根目录 `AGENTS.md` 定义。

## 1. 新依赖真实性预检
引入外部包之前，先核实包的真实身份和来源，避免拼写错误、仿冒包或不存在的版本。

- 核对包名、官方仓库/注册表、目标版本、许可证及维护信息。
- Node.js 可尝试 `npm view <package> name version time.modified license repository.url`；Python 可尝试 `pip index versions <package>` 或查看 PyPI 项目元数据。具体命令必须根据当前环境确认可用，不得假设工具已安装或网络必然可用。
- 将本机实际验证可用的项目命令记入项目环境说明（若项目采用该文档），并标注验证日期。
- 真实性核验失败或来源无法确认时暂停该依赖的引入，报告具体缺口；不能把网络失败解释为依赖不存在，也不能默认放行。
- 依赖审批、许可证策略、漏洞检查和维护门禁以 `04-reuse-and-supply-chain.md` 为唯一权威定义。

## 2. 可复现的验收证据
- 对可由 CLI 检查的技术任务，提供可复现命令及真实结果；退出码只有在实际获得时才能报告。
- 不使用 `|| true`、吞掉错误码或仅靠 `echo` 伪造通过。若命令被包装器或 CI 吞掉状态，先核查真实执行状态。
- 不要求每个非技术步骤都配 CLI 命令；文档任务可以使用实际文件差异或渲染预览，UI 任务可以使用截图、浏览器检查或项目规定的视觉回归方式。
- 关键验证尽可能设计成能够失败的断言。必要时采用安全的反向测试来确认检测能力，但不得破坏用户数据或真实服务。

## 3. 完成状态用语
- **已验证**：提供与具体需求匹配的实际证据。
- **未验证**：明确说明尚未执行、无法执行或证据不足。
- **不确定**：说明仍存在的未知、假设或环境差异。
- 不得用“无报错”“命令已发出”代替验证成功；不得将单项测试结果夸大为全部需求验收。
