# 08-Orchestration and Multi-Agent Guard

> **核心宗旨**：多智能体协作模式（Teamwork）与深度代理（Boost / DeepCoder / DeepInvestigator）具备强大的并发攻坚能力，但也存在高昂的“通信税”、“无限评审死循环”与“盲目重试泥潭”三大毒点。本规约建立硬性收敛门禁，确保算力花在刀刃上。

---

## 一、 多智能体协作收敛规约（适用于 /teamwork-preview 或等效多 Agent 协作模式）

### 1. 单兵优先准则 (Solo First)
- **触发门禁**：仅在跨 3 个以上独立模块、或需要大规模并行文献/架构方案对抗评审时才允许拉起 Teamwork 团队；
- **自包含任务严禁团队化**：任何单文件 Bug 修复、局部功能扩展、同模块组件与样式联动，必须坚决使用 Solo（单 Agent）闭环，严禁为简单任务拉起完整流水线（防止 80% Token 消耗在 Agent 之间互相打招呼与交接文档）。

### 1-B. 子代理硬约束继承 (Constraint Inheritance)
- **硬约束显式注入**：调度器将任务下发给子代理时，必须在提示词中显式注入以下硬约束：网络域名白名单限制、密钥零容忍（不打印/读取/提交 `.env` 与密钥）、破坏性与高危操作审批门禁、2 次同类错误熔断、真实命令证伪测试门禁；
- **主代理独立复验**：主代理必须独立复核子代理报告的“已通过”结论（至少抽验关键命令输出与退出码）；
- **文件写入防撞车**：并行子代理不得同时修改同一文件。

### 2. Review 轮次双轮熔断锁 (Max 2 Rounds)
- **无限找茬拦截**：实现型 Agent (Coder) 与审查型 Agent (Reviewer) 之间的交互上限严格设定为 **2 轮**；
- **熔断升格**：若经过 2 轮代码迭代后，Reviewer 依然提出新的**非阻断性**细节建议，禁止进入第 3 轮交互；必须自动向 PM 呈报【PM 决策卡片】，由人类决定是采纳当前成果还是人工指明修改方向；
- **阻断性问题直通车**：若 2 轮评审后仍存在**阻断性问题**（如核心安全隐患、数据丢失风险、架构契约破坏），立即直接上报 PM 决策，严禁进入第 3 轮无休止拉扯。

---

## 二、 深度代理调度与防盲目重试门禁（适用于 /boost 或等效深度推理代理）

### 1. 意图自洽与前置无歧义检查 (High-Fidelity Prompt Guard)
- **严禁孤立代词下发**：在将用户任务转交给 DeepCoder / DeepInvestigator 之前，调度器必须确保提示词中不包含脱离上下文的孤立代词（如“继续刚才的那个”、“把那几个改了”）；必须自动在 Additional Context 中补齐具体受影响的文件绝对路径与前置事实。

### 2. 算力无底洞熔断 (Anti-Retry Sinkhole)
- **重试上限锁**：当子代理执行结果出现用例未通过或边界缺陷时，追加轮次（Spawn additional round）上限严格设为 **2 次**；
- **禁止原地死循环**：若连续 2 轮子代理仍无法解决同一类报错，调度器必须立即终止盲目追加，向用户生成【熔断受阻与错误报告卡片】，列出根因与可选出路，严禁在错误方向上空耗深度思考算力。
